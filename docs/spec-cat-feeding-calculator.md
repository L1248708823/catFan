# 猫咪喂养计算工具实施规格

**日期：** 2026-10-09  
**依据：** 已确认的 PRD、领域词汇、ADR 与本次对话  
**状态：** 可用于拆分功能实施任务，视觉方案待定  
**发布状态：** 当前未配置任务系统，尚未发布，也未应用 `ready-for-agent` 标签

## Problem Statement

用户需要根据猫咪资料获得可查阅依据的每日热量参考区间，再按自己实际购买的食品换算重量或包装数量，并保存体重和历史计算。重复打开应用后，应能继续上一次操作。

用户同时使用手机浏览器和 PC，期望常用功能在两端都可操作。首屏应优先展示结果和必要输入，公式、系数、食品背景信息及来源放入计算详情，减少主视图的解释性内容。

现有项目只有 PRD、领域词汇、两份 ADR 和独立 HTML 原型，没有生产应用、数据库或现成测试。三种原型均未被用户选中，原型中的示例数值、静态弹窗及布局不能作为实施依据。

## Solution

建设一个响应式、Mobile-first、Local-first PWA，使用同一套 Web 应用覆盖 PC 与 H5。首期支持一只猫，数据关联为后续多猫扩展保留空间。

优先完成资料录入、计算、食品换算、快照保存和本地恢复的完整流程，再完善历史趋势、备份与离线能力。功能开发使用成熟组件和基本响应式布局，后续根据真实网站参考确定视觉设计并调整展示层。

热量模型独立展示，食品换算使用一个明确的“当前换算依据”。计算结果自带公式、所用类别、输入与来源，详情界面直接展示这些信息，使规则可查阅。

## User Stories

1. 作为养猫用户，我希望在手机和 PC 上完成同一套操作，以便在不同使用场景中管理数据。
2. 作为首次使用者，我希望先看到添加猫咪的入口，以便建立自己的资料。
3. 作为养猫用户，我希望填写名称、出生日期、性别、绝育状态和首次体重，以便生成第一份计算。
4. 作为养猫用户，我希望填写品种、BCS、生活方式和备注，以便保留相关观察信息。
5. 作为养猫用户，我希望档案当前体重取最近一条有效体重记录，以便避免两处体重数据不一致。
6. 作为养猫用户，我希望新增体重时自动记录时间，以便减少录入步骤。
7. 作为养猫用户，我希望能更正录入错误的资料和体重，以便保持记录准确。
8. 作为养猫用户，我希望根据完整月龄划分幼猫阶段，以便在阶段边界得到明确的结果。
9. 作为养猫用户，我希望默认使用 FEDIAF 2025，并可启用 AAHA 2021，以便按需要查看不同指南的结果。
10. 作为养猫用户，我希望两个模型分别展示热量区间，以便看到各自的估算结果。
11. 作为养猫用户，我希望明确选择食品换算采用哪个模型，以便理解食量结果的依据。
12. 作为养猫用户，我希望使用基础资料确定 AAHA 类别，并能主动选择活动较少或容易肥胖，以便采用对应的公开规则。
13. 作为养猫用户，我希望查看本次公式、系数、类别、年龄阶段和来源，以便确认没有隐藏参数。
14. 作为养猫用户，我希望主计算视图只显示必要信息，以便快速查看结果。
15. 作为养猫用户，我希望录入干粮、湿粮、餐包、冻干、零食和其他食品，以便使用自己的食品库。
16. 作为养猫用户，我希望按包装提供的 kcal 或 kJ 单位录入热量，以便减少手动换算。
17. 作为养猫用户，我希望只在需要时填写每罐或每份餐包重量，以便避免记录整袋干粮重量等无用信息。
18. 作为养猫用户，我希望只有每包装热量的食品仍可按包装数量计算，以便使用标签信息不完整的食品。
19. 作为养猫用户，我希望系统只展示数据足够支持的单位，以便避免得到猜测的重量或包装数。
20. 作为养猫用户，我希望在食品或计算详情查看用途、营养完整性、热量来源和备注，以便主视图保持简洁。
21. 作为养猫用户，我希望选择干粮后看到单纯干粮用量，以便获得每日克数范围。
22. 作为养猫用户，我希望选择湿粮后看到单纯湿粮用量，以便获得克数和可用的包装数量范围。
23. 作为养猫用户，我希望输入湿粮数量后看到剩余干粮范围，以便比较干湿混合的用量。
24. 作为养猫用户，我希望输入餐包数量后看到剩余干粮范围，以便比较餐包加干粮的用量。
25. 作为养猫用户，我希望四类视图只在选择对应食品时出现，以便页面匹配当前操作。
26. 作为养猫用户，我希望数量变化实时更新结果，以便连续调整，无需反复保存。
27. 作为养猫用户，我希望辅助食品超过区间上限时得到明确状态且没有负食量，以便识别当前选择的结果。
28. 作为养猫用户，我希望主动保存本次计算，以便保留真正需要的历史结果。
29. 作为养猫用户，我希望修改食品或猫咪资料后旧快照仍保持原值，以便可靠地回看历史。
30. 作为养猫用户，我希望重新打开应用后恢复猫咪、体重依据、模型、食品和数量，以便继续上次操作。
31. 作为养猫用户，我希望新增体重后由我决定是否重新计算，以便保留当前结果的明确依据。
32. 作为养猫用户，我希望查看真实体重记录点和历史列表，以便观察变化并回查原始记录。
33. 作为养猫用户，我希望导出完整 JSON 备份，以便在浏览器数据丢失或换设备后恢复。
34. 作为养猫用户，我希望导入前查看摘要并确认覆盖，以便了解恢复操作的影响。
35. 作为养猫用户，我希望导入失败时原数据仍存在，以便避免不完整文件破坏已有记录。
36. 作为养猫用户，我希望导出 CSV，以便在表格软件中查看核心数据。
37. 作为养猫用户，我希望完成首次缓存后仍能离线使用核心功能，以便在没有网络时记录和计算。
38. 作为养猫用户，我希望版本更新保留本地数据和历史快照，以便持续使用应用。

## Implementation Decisions

### 1. 实施顺序与视觉范围

先完成数据结构和业务流程，再确定最终视觉。功能版本从第一阶段起适配 PC/H5，不能把手机端关键导航、模型选择或食品操作隐藏起来。

开发按可运行的完整流程推进：

1. 项目基础、数据结构、猫咪档案、首次体重、默认模型计算和详情展示。
2. 食品库、单位标准化、单一食品换算及两个混合视图。
3. 草稿恢复、显式保存计算快照、新体重重新计算入口。
4. 体重趋势、计算历史、JSON 备份恢复和 CSV 导出。
5. PWA 安装、离线缓存及完整功能验收。
6. 根据成熟产品参考确定视觉，调整布局、配色、字排和组件样式，再复核已有流程。

备份恢复在首期完成，涉及数据版本的设计从第一阶段纳入。上述顺序描述交付能力，不把数据设计、计算引擎和界面拆成长期无法运行的孤立阶段。

现有 A/B/C 原型均为未采纳的探索材料，不继承其产品名称、配色、侧栏、卡片结构或手写图表。

### 2. 技术基础

| 领域 | 选择 | 用途 |
| --- | --- | --- |
| 应用 | React + TypeScript + Vite | 静态 Web 应用和本地开发 |
| 样式 | Tailwind CSS | 响应式布局与组件样式 |
| 基础组件 | shadcn/ui，统一选用一套底层交互组件 | 复用表单、弹窗、抽屉、标签、按钮等成熟实现 |
| 图标 | Lucide React | 使用一致的图标体系 |
| 图表 | Recharts，可复用 shadcn/ui Chart | 体重折线、真实记录点、坐标轴与数据提示 |
| 本地数据 | IndexedDB + Dexie | 离线构建的持久化实现，见 ADR 0003 |
| 服务端数据 | Fastify + mysql2 + MySQL 8 | 默认构建的持久化实现，见 ADR 0003 |
| 导入校验 | Zod | 校验结构、数值、单位和版本 |
| PWA | manifest、service worker，可采用 vite-plugin-pwa | 安装与静态资源离线缓存 |
| 部署 | nginx 静态托管 + `/api` 反代 + systemd | 首次访问、资源获取和更新 |

具体依赖版本在项目初始化时选兼容的稳定版本并锁定。当前只作规格，不安装依赖、不建立生产工程。

页面使用共享的颜色、字体、间距和圆角变量，图表颜色与组件主题一致。业务结果中不保存 Tailwind 类名、图标名称或布局信息。

### 3. 模块边界

| 模块 | 负责内容 | 对外结果 |
| --- | --- | --- |
| 领域计算 | 月龄、模型规则、食品热量标准化和混合换算 | 结构化数值、计算状态与可追溯过程 |
| 本地数据 | 档案、体重、食品、草稿和快照的读写及迁移 | 可供计算和展示使用的领域数据 |
| 应用流程 | 首次录入、切换模型、更新数量、保存、恢复 | 当前计算状态及用户操作反馈 |
| 展示 | 导航、表单、结果、详情和图表 | PC/H5 用户界面 |
| 备份恢复 | 导出格式、校验、预览和原子覆盖 | 完整文件或明确的恢复结果 |

领域计算接收普通数据，返回普通数据，不依赖 React、浏览器 DOM、数据库或组件库。时间作为输入传入，不能在同一次计算中各自读取时间产生不同月龄。

界面读取结构化结果生成主视图与详情，公式、系数和来源只由模型规则提供，避免详情文字与实际计算分别维护。

本地数据接口集中管理读写，不让页面任意访问各张存储表。不创建插件系统、通用工作流引擎或多套可同时启用的数据库适配器。

> 修订：数据层改为仓储端口加两套实现（Dexie 与 HTTP），由构建期的 `VITE_DATA_BACKEND` 二选一，见 [ADR 0003](adr/0003-server-backed-storage.md)。这是构建期选择而不是运行时可切换的多适配器，任一产物只有一个真相源，原约束要防的双写分叉问题仍然被禁止。

这组边界支持后续 UI 调整：可重写布局与展示组件，继续使用现有计算接口、数据结构、快照和备份格式。组件结构与表单交互仍可能需要调整，迁移成本取决于这些边界是否保持清晰。

### 4. 数据结构

| 对象 | 主要字段 | 约束 |
| --- | --- | --- |
| 猫咪档案 | 稳定 ID、名称、出生日期、性别、绝育状态、品种、BCS、生活方式、备注、创建与更新时间 | 一期最多一只；不重复存储独立可编辑的当前体重 |
| 体重记录 | 稳定 ID、catId、体重 kg、记录时间、时区偏移、备注、更新时间 | 体重大于 0；首次建档同时创建第一条记录 |
| 食品 | 稳定 ID、名称、用途、形态、原始热量值与单位、包装单位名称、每份重量、每份热量、营养完整性、来源、备注、时间 | 食品库共享；餐包仍属于湿粮形态，包装单位独立记录 |
| 当前计算草稿 | 当前 catId、体重记录引用及输入副本、评估日期、已启用模型、换算依据、AAHA 选项、食品选择与数量、当前计算视图 | 自动恢复的当前工作状态，不属于历史快照 |
| 模型规则 | 稳定模型 ID、指南名称与年份、规则版本、公式 ID、条件类别、系数、来源定位与 URL | 规则随应用版本提供，不由界面临时构造 |
| 计算快照 | 稳定 ID、catId、保存时间、评估日期、档案输入副本、体重输入副本、模型结果与规则副本、换算依据、食品参数副本、数量与换算结果 | 完整保留当时的数据和计算过程，不依赖后来编辑的对象 |
| 备份文件 | 格式标识、导出格式版本、数据结构版本、应用版本、导出时间、全部核心数据与草稿 | JSON 用于完整恢复；校验通过后才能写入 |

模型规则版本、数据库结构版本与 JSON 格式版本分别管理，各自反映对应内容的变化。数据库结构更新通过明确迁移完成，不能用清空数据库完成升级。

日期类和时间类字段区分保存：出生日期、计算评估日期采用日期值；记录和保存时刻采用 ISO 时间戳，并保留当时的时区偏移。列表按时间戳排序，展示时使用本地时间。

保存档案与第一条体重记录、保存快照以及导入覆盖均需要一致性保障。任何一步失败都不能留下半份资料或半份备份。

### 5. 首次使用、编辑与恢复

首次无档案时，主入口为添加猫咪。完成必填资料和首次体重后进入计算，默认启用 FEDIAF 2025；无食品时显示添加食品入口，模型结果仍可查看。

出生日期必填且不能晚于评估日期，名称不能空白，体重与能量密度必须为有限正数。年龄按完整月数计算；月末生日遇到目标月无对应日时，以该月最后一天作为当月周年日，属于实施采用的日历规则。

当前体重由最新有效体重记录派生。新增体重只更新档案摘要和最新记录，不自动覆盖当前草稿的计算依据；用户主动使用新体重后更新当前计算。保存的快照保持原样。

草稿保存当时用于计算的输入副本，恢复时先展示其明确的体重和评估日期。食品或档案修改进入新的计算，不静默替换旧草稿里的输入；用户重新选择或明确重新计算时采用最新数据。

14 天和 30 天体重更新时间阈值沿用 PRD，属于不阻断操作的产品提醒；详细解释置于详情层。修改体重记录仍不改变历史快照。

一期支持新增、查看、编辑，没有删除猫咪、食品、体重或快照的入口。JSON 覆盖恢复属于已确认的数据替换流程。

### 6. 模型计算合同

计算输入包括体重 kg、出生日期、评估日期、绝育状态、FEDIAF 生活方式和用户明确选择的 AAHA 选项。输出包括模型 ID、原始数值区间、所用类别、月龄阶段、边界日期、公式、系数、输入、计算步骤、来源和状态。

FEDIAF 和 AAHA 沿用 PRD 规定的公式与系数。年龄阶段按 4、9、12 个月生日切换。FEDIAF 明显活跃选项由用户选择；AAHA 的活动较少或容易肥胖选项独立记录，不能从室内属性自动推断。

AAHA 未满 12 个月使用 2.5；成年且显式选择活动较少或容易肥胖时使用 1.0；其余成年猫按绝育状态使用相应区间。已允许记录绝育状态未知，因此未知时需要补齐 AAHA 分类所需的信息后再输出该模型结果，不猜测系数；其他具备条件的模型可继续使用。

默认启用 FEDIAF，至少有一个已启用模型。当前换算依据只能是已启用且具备完整计算输入的模型；关闭当前依据时，转到另一可用模型并明确显示其名称，若没有可用结果则保留录入入口。

两个模型结果始终独立，不合并、不取平均。食品视图全部使用当前换算依据，快照保存这个模型选择。

中间结果保留精度，只在展示层取整：每日 kcal 和克数展示到整数，包装数量展示到两位小数；相同上下限可以显示单值，但内部仍保留区间。计算详情说明采用的显示精度。

按 PRD 公式，3.8 kg 室内或已绝育成年猫的 FEDIAF 原始区间为 127.191577～183.449390 kcal/day，整数显示为 127～183；AAHA 已绝育成年猫为 228.621455～266.725030，整数显示为 229～267。旧原型中的 247～356 不能用于此示例。

模型开发时逐项对照 PRD 所列原始指南，保留核对到的章节、表格或页码。当前规格继承既定规则，公式算术复核不等于已重新验证所有指南内容；如果核对发现差异，需要记录来源差异并明确处理，不能静默改动。

### 7. 食品和四种计算视图

食品保留用户原始输入和单位，统一换算为可用的 kcal/g 或 kcal/包装。kJ 使用 1 kcal = 4.184 kJ 标准化。

只填写每包装热量时，支持包装数量和包装输入的混合计算，克数结果为空；同时有包装重量时可推导克数。密度型输入加包装重量可推导包装热量。重复录入两种热量口径时，必须明确计算采用的原始口径，不能静默选值造成详情与数值不一致。

食品表单按实际需要展开包装字段，用户只填写热量和每罐或每份餐包重量等必要数据，不做包装整数候选或最接近整数推荐。单纯湿粮也可选择餐包；餐包加干粮视图通过包装选择识别，避免把餐包误建成独立营养类型。

首页最多四种视图，分别由必要选择触发：

| 视图 | 出现条件 | 结果 |
| --- | --- | --- |
| 单纯干粮 | 已选择可按重量计算的干粮 | 干粮 g/day 区间 |
| 单纯湿粮 | 已选择具有可用热量的湿粮，包括餐包 | 可计算的克数和/或包装数量区间 |
| 干湿混合 | 已选择干粮和辅助湿粮，并输入数量 | 辅助湿粮用量、剩余干粮范围 |
| 餐包加干粮 | 已选择干粮和按份输入的餐包，并输入数量 | 餐包份数、剩余干粮范围 |

必要食品选择齐全时四种视图可同时显示；食品库数量不受四种视图限制。辅助零食只计入对应混合计算，不额外创建独立主视图，也不把不同视图的食品热量互相叠加。

辅助食品数量允许非负数，用户可按克或配置好的包装单位输入。混合计算从区间两端分别扣除辅助食品热量，结果最小为 0；超过上限时显示简短状态和 0 干粮，详情保留实际超出量。

当前数量变化只更新草稿。用户主动保存时创建独立快照；读取快照使用保存值，不用最新公式或食品重新算一遍。

食品用途、完整性、数据来源和备注在食品详情或计算详情查看，主视图保留食品、数量、结果、单位和必要的操作反馈。

### 8. 历史、图表、备份与离线

体重曲线只展示真实记录，不预测。采用成熟图表组件显示坐标、记录点和记录详情，同时保留可查阅的记录列表。计算历史展示保存时间、当时月龄、体重、模型、区间、食品与数量，并可进入计算详情。

JSON 包含全部核心数据、当前草稿、版本及快照里的公式依据。导入分为读取校验、摘要预览、用户确认和事务覆盖；确认前不修改数据。拒绝多猫文件、未来不兼容版本、非法数值和失效引用，写入失败保留原数据。成功后恢复导入状态，不叠加旧记录。

CSV 只导出，不用于恢复。猫咪、体重、食品和计算快照分别输出对应表格，快照按模型或视图展开关联行，保留 ID 以便追溯。输出 UTF-8，文本字段正确转义，时间与单位明确。

缓存应用静态资源，业务数据保存在 IndexedDB。首次访问需要网络；完成缓存后，核心计算、记录、历史和备份功能可离线使用，指南外链仍需要网络。更新应用资源时保留业务数据，数据迁移由版本机制完成。

### 9. 后续 UI 借鉴计划

页面仍覆盖计算、体重记录、食品库、计算历史和数据管理，具体导航与布局等待成熟参考选定。首期视觉调整不能减少已有功能，也不能把 PC 侧栏直接隐藏来替代 H5 导航。

整体视觉参考应从真实产品页面或有完整页面的设计稿中选择，可以来自不同领域。选定参考时记录原始 URL、对应页面截图及具体借鉴内容，至少覆盖 PC/H5 导航、结果区、表单或详情和记录图表。营销首页只能补充配色或字排参考，不能单独代表应用工作区。

用户指定的 Beautiful UI、Be UI、Rare UI、Transitions 和 shadcn/ui 用作局部组件灵感。采用一个主要视觉方向，再用成熟组件实现细节；成熟组件选型不等于已经完成整体设计。

图标统一使用 Lucide，体重图表统一使用 Recharts。配色和字排从最终选定参考提炼成共享主题变量，不继承未采纳原型的绿色主题。动效只帮助切换、展开和反馈，不引入额外页面内容。

主视图减少重复解释、状态徽章与装饰性模块，关键结果和操作优先；公式、系数、来源与食品背景信息进入详情。用户未选择任何现有原型，视觉方案保持待定。

## Testing Decisions

1. 已确认跳过单元测试，不把 TDD 或补写单元测试设为实施前置。本次是规格工作，不新增或运行功能测试。
2. 验证以浏览器中的完整用户流程为最高边界，观察用户可见结果、刷新后的数据和导出文件，不依赖组件内部状态、数据库私有实现或调用次数。
3. 涉及验证的能力包括首次录入、两个模型、单位换算、四种条件视图、快照不变、草稿恢复、覆盖导入、体重图表、PC/H5 操作及离线使用。
4. 项目暂无现成测试和可复用测试流程。自动化 E2E 尚未确认启用；若实施阶段选择 E2E，遵循用户要求在完成后执行，产出可重复场景、截图或导出工件，不在开发期间运行全套。
5. 功能阶段至少完成类型检查、构建和人工完整流程验收；不为低影响样式调整补测试。验收保存输入、期望结果、实际结果及 JSON/CSV 或截图工件。
6. 首批验收覆盖 4/9/12 个月边界、3.8 kg 成年猫公式样例、只含包装热量的食品、辅助热量等于下限或超过上限、食品修改后旧快照不变、非法 JSON 不影响原数据。
7. PC/H5 复核关键导航、表单、换算依据和详情入口均可用。视觉替换后复走已有完整流程，并与替换前导出数据及相同输入的计算结果对照。

## Out of Scope

首期不做账号、多用户、多猫管理界面、原生打包或应用商店发布。业务后端已由 [ADR 0003](adr/0003-server-backed-storage.md) 纳入范围：数据存在服务器 MySQL，但没有账号体系，接口靠网络隔离兜底。

不做疾病诊断、专项减重、妊娠哺乳模型、处方粮推荐、自动增减食量、任意系数滑动条、长期喂养排程、模型结果融合或所有食品组合穷举。

不做食品数据库抓取、包装整数推荐、CSV 导入、多猫 JSON 导入、JSON 合并、自动预测曲线或聊天式 AI 助手。删除入口已纳入范围：删除猫咪（连带其体重、草稿和快照）、删除单条体重记录、删除单条快照，都是硬删除，见 ADR 0003。

本次不开发生产功能、不修订旧原型为定稿、不选择最终颜色与布局，也不安装依赖。
